# MyBatis-Plus

## 数据访问抽象（未学习）

### MyBatis 映射基础（未学习）

1. 目标：理解 MyBatis-Plus 建立在 SQL 映射和参数绑定之上的运行边界。
2. 前提：框架仍需将方法调用转换为 SQL，并将结果映射为对象。
3. 推导 1：通用能力复用底层映射机制，而不是替代数据库执行。
4. 推导 2：自定义语句仍可通过原有映射接口接入。
5. 结论：掌握 MyBatis 映射基础是使用 MyBatis-Plus 的必要前提。
6. 边界：具体注解、XML 和插件行为受版本及配置影响。

### Mapper 与 SQL 映射（未学习）

1. 目标：明确 Mapper 接口方法与 SQL 语句、参数及结果之间的对应关系。
2. 前提：Mapper 方法签名定义调用契约，映射配置定义执行细节。
3. 推导 1：通用 Mapper 方法可由框架按实体元数据生成语句。
4. 推导 2：未覆盖的查询可声明自定义方法并绑定 XML 或注解 SQL。
5. 结论：Mapper 是调用边界，SQL 映射是实现边界，两者可分离演进。
6. 边界：方法名相同但参数或返回类型不一致会导致绑定或装配错误。

### 参数和结果映射（未学习）

1. 目标：保证条件参数、实体字段与查询结果在类型和语义上保持一致。
2. 前提：实体属性、数据库列和类型处理器共同决定转换规则。
3. 推导 1：框架根据元数据生成参数占位和列映射。
4. 推导 2：自定义投影或连接结果需要显式别名、映射或结果对象。
5. 结论：统一参数与结果契约可降低通用操作和自定义 SQL 的组合风险。
6. 边界：复杂嵌套、数据库特有类型或计算列可能超出默认映射能力。

### 通用 CRUD 如何减少重复 SQL（未学习）

1. 目标：用统一接口覆盖稳定的单表增删改查，减少重复语句维护。
2. 前提：实体与表结构映射稳定，操作语义符合通用模板。
3. 推导 1：框架依据主键、字段元数据生成基础 CRUD 语句。
4. 推导 2：调用方通过统一方法传递实体或条件对象即可执行操作。
5. 结论：通用 CRUD 适合规则明确的单表操作，可降低样板代码量。
6. 边界：复杂连接、聚合、批量策略和特殊锁语义通常需要自定义 SQL。

### 条件构造器如何表达可移植查询（未学习）

1. 目标：以结构化条件对象表达常见筛选、排序和更新条件。
2. 前提：条件由字段、运算符和值组成，值可参数化绑定。
3. 推导 1：构造器将条件节点组合为框架可解析的查询模型。
4. 推导 2：框架负责生成占位参数和连接词，调用方避免手工拼接。
5. 结论：条件构造器适合常见、跨数据库可表达的查询组合。
6. 边界：方言函数、复杂子查询或精细 SQL 控制可能需要回到手写语句。

### 复杂方言查询何时回到自定义 Mapper（未学习）

1. 目标：在保留框架通用性的同时使用数据库特有查询能力。
2. 前提：目标语义依赖特定方言，或构造器生成的 SQL 难以验证和优化。
3. 推导 1：将方言 SQL 放入自定义 Mapper，保持参数和结果契约稳定。
4. 推导 2：上层继续通过 Mapper 调用，不扩散方言文本。
5. 结论：复杂方言场景应使用自定义 Mapper，而非强行套用通用构造器。
6. 边界：自定义语句提高迁移成本，需单独维护数据库版本兼容性。

## MyBatis 与 MyBatis-Plus 协作（未学习）

### 生成式能力与手写 SQL 如何分工（未学习）

1. 目标：划分自动生成语句与人工编写语句的职责，保持访问层可维护。
2. 前提：自动生成擅长重复模式，手写 SQL 擅长复杂关系和方言能力。
3. 推导 1：稳定单表操作交给通用能力，减少模板代码。
4. 推导 2：复杂查询保留在 XML 或注解中，并复用统一结果对象。
5. 结论：按查询复杂度分工可同时获得开发效率和 SQL 可控性。
6. 边界：分工标准需结合团队规范、数据库兼容目标和性能要求调整。

### 扩展能力如何保持结果映射契约（未学习）

1. 目标：在引入插件、分页或自定义方法后保持返回结构稳定。
2. 前提：扩展可能改写 SQL、增加参数或改变结果集列。
3. 推导 1：先定义返回对象及字段语义，再约束扩展对列集的影响。
4. 推导 2：对新增列、别名和嵌套关系更新显式映射配置。
5. 结论：以结果映射契约作为扩展边界，可避免上层因 SQL 改写而失配。
6. 边界：插件组合顺序、分页方言和自定义类型处理器可能引入额外差异。
