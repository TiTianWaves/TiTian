# PostgreSQL

## PostgreSQL 增强能力（未学习）

### 如何用 DISTINCT ON 表达每组首行（未学习）

1. 目标：在 PostgreSQL 中为每个分组直接取得排序后的首行。
2. 前提：查询必须同时指定 `DISTINCT ON` 的分组列和决定首行的排序列。
3. 推导 1：`DISTINCT ON (k)` 先按 `ORDER BY` 形成以 `k` 开头的有序结果。
4. 推导 2：同一 `k` 的多行中，排序最先出现的行被保留，其余行被去重。
5. 结论：`DISTINCT ON` 可在一次查询中表达“每组一行”，并由排序决定保留哪一行。
6. 边界：`ORDER BY` 未提供稳定的组内次序时，保留行不具备确定性；该语法不是 SQL 通用语法。

### 数组与 JSONB 如何支持复合数据查询（未学习）

1. 目标：在 PostgreSQL 中查询一列内的多值或半结构化数据。
2. 前提：数组保持同质元素和位置信息，`jsonb` 以二进制格式存储 JSON 对象或数组。
3. 推导 1：数组运算符可判断包含、重叠等集合关系，数组下标可访问指定位置。
4. 推导 2：`jsonb` 运算符可按键、路径和结构匹配对象或数组内容。
5. 结论：数组适合结构稳定的多值属性，`jsonb` 适合结构可变且需要键路径查询的数据。
6. 边界：两者都不会自动替代关系建模；跨元素约束、复杂关联和高选择性检索仍可能需要拆表。

### GIN 如何索引数组与 JSONB（未学习）

1. 目标：为数组成员或 `jsonb` 内部键值查询提供倒排访问路径。
2. 前提：GIN 将一行值拆成多个键项，并记录每个键项对应的行位置。
3. 推导 1：查询条件先定位匹配的键项集合，再合并得到候选行。
4. 推导 2：候选行仍需按运算符和可见条件复核，索引不保证直接返回最终结果。
5. 结论：GIN 适合成员、包含和路径存在性等多键检索，能避免逐行扫描整列复合值。
6. 边界：GIN 体积和更新成本通常高于 B-tree；不适合仅有单一标量等值或范围条件的列。

### 部分索引如何缩小索引维护范围（未学习）

1. 目标：只为满足稳定谓词的行建立 PostgreSQL 索引。
2. 前提：创建索引时使用 `WHERE` 谓词，查询条件必须能证明该谓词成立。
3. 推导 1：不满足谓词的行不写入索引，从而减少索引页、扫描行和更新维护。
4. 推导 2：优化器在查询谓词蕴含索引谓词时，才会将该索引作为可用路径。
5. 结论：部分索引可将索引资源集中在未删除、已审核等高价值子集上。
6. 边界：谓词变化或无法被优化器证明时索引可能不被使用；MySQL 没有同等通用的部分索引语法。

### INCLUDE 如何携带非键列（未学习）

1. 目标：在不扩大索引排序键的情况下，让查询从 PostgreSQL 索引直接取得附加列。
2. 前提：`INCLUDE` 列存储在索引项中但不参与键比较、去重或排序。
3. 推导 1：键列负责定位和有序扫描，包含列负责补齐投影所需值。
4. 推导 2：当可见性检查允许时，查询可使用索引仅扫描而无需访问堆表。
5. 结论：`INCLUDE` 提供了键语义与覆盖读取的分离，适合少量只读投影列。
6. 边界：包含列仍增加索引体积和写入成本，且可见性映射不满足时仍需回表；MySQL 没有同名非键列机制。

## PostgreSQL 与 MySQL 的能力边界（未学习）

### 部分索引与索引条件表达能力差异（未学习）

1. 目标：评估 PostgreSQL 条件索引迁移到 MySQL 时的可替代性。
2. 前提：PostgreSQL 部分索引把行过滤谓词写入索引定义，MySQL 常规索引不带行过滤谓词。
3. 推导 1：PostgreSQL 可直接缩小索引维护集合，MySQL 需要生成列、函数索引或应用层拆分来编码条件。
4. 推导 2：替代方案把条件结果物化为列值，索引维护和查询谓词因此改变了语义边界。
5. 结论：两者都能利用选择性条件优化访问，但 PostgreSQL 是索引级过滤，MySQL 多为数据模型级模拟。
6. 边界：生成列或函数索引的可用性取决于 MySQL 版本与表达式限制，不能视为完全等价迁移。

### 数组、JSONB 与 MySQL 类型系统差异（未学习）

1. 目标：选择可迁移的复合数据表示并评估查询代价。
2. 前提：PostgreSQL 提供原生数组和 `jsonb`，MySQL 没有独立数组类型但提供原生 `JSON`。
3. 推导 1：PostgreSQL 数组可用数组运算符和专用索引表达集合操作，MySQL 数组通常编码为 JSON 数组。
4. 推导 2：PostgreSQL `jsonb` 支持二进制结构比较和 GIN，MySQL JSON 查询通常依赖路径表达式、生成列或多值索引。
5. 结论：迁移时 JSON 文档可保留概念，但数组类型、操作符和索引实现必须重写。
6. 边界：两种数据库的 JSON 标准函数、路径语法、类型转换和索引覆盖范围不同，不能仅替换列类型。

### 标识符大小写与时间类型的迁移差异（未学习）

1. 目标：避免 PostgreSQL 到 MySQL 迁移时出现列名解析和时间语义变化。
2. 前提：PostgreSQL 未加引号的标识符折叠为小写，加双引号后按大小写精确匹配；MySQL 使用反引号，表名大小写还受平台和配置影响。
3. 推导 1：带引号的驼峰列名在 PostgreSQL 中要求每次精确引用，迁移到 MySQL 后解析规则和大小写敏感性可能改变。
4. 推导 2：PostgreSQL `timestamptz` 保存绝对时刻并按会话时区显示，MySQL `TIMESTAMP` 会进行时区转换而 `DATETIME` 不保存时区。
5. 结论：迁移必须统一标识符命名策略，并明确时间列是绝对时刻还是无时区本地日期时间。
6. 边界：具体表名大小写行为受操作系统和 MySQL `lower_case_table_names` 等配置影响，不能只依据 SQL 文本判断。
